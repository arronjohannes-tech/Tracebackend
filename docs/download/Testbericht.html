2. Was geprüft wurde

  • Backend: Anmeldung, Mandantenzuordnung, Rollen-/Routenverhalten, Kryptografie, Geometrie-/SOAP-Hilfsfunktionen, DDS-Wiederholungen, Geofence-Freigabe und Architekturgrenzen.
  • Neue DDS-Regression: Ein neuer Validierungsschlüssel darf weder submitting noch reconciliation_required zurücksetzen.
  • Mobile: Authentifizierung, transienter Refresh-Fehler versus ungültige Sitzung, lokale mandantenbezogene Ablage, fachliche Regeln und Geofence-Sync-Verhalten.
  • Web: Rollenregister, fachliche Hilfsregeln und Übersetzungsschlüssel des Web-Prototyps.
  • PostgreSQL: Ein späterer Schreiber derselben Organisation wartet bis zum Abschluss des früheren Schreibers; ein fortgeschriebener Cursor kann anschließend beide Änderungen lesen. Rollbacks erzeugen zulässige Lücken, ohne bestätigte Änderungen zu verlieren.
  • Versionsvergleich: Eine veraltete Ausgangsrevision wird unabhängig von der Geräteuhr abgewiesen.
  • iOS-Export: Metro/Expo erzeugt das iOS-JavaScript-/Hermes-Bundle einschließlich referenzierter Ressourcen.

3. Testumgebung und Grenzen

Die Prüfungen wurden lokal unter Windows mit der im Backend bereitgestellten Node-24-Laufzeit ausgeführt. Die Datenbankprüfung verwendet eine eigene, nur an 127.0.0.1 gebundene PostgreSQL-18-Testinstanz mit zufällig gewähltem Port und Kennwort; sie wird nach dem Test beendet.

Die zusätzliche Datenbankprüfung wendet Migration 004 auf minimalen Tabellen an. Sie prüft nicht die vollständigen Migrationen 001–004 mit PostGIS, nicht alle RLS-Policies unter produktiven Rollen und nicht die reale Datenbankkonfiguration. Viele Backend-Routentests verwenden Datenbank-Doubles.

Der Erfolg des iOS-Exports bestätigt weder einen signierten nativen Build noch Installation, TestFlight-Zulassung, GPS-Verhalten, Hintergrundübertragung oder VoiceOver auf einem echten iPhone. S3 und die externe DDS-Live-Anbindung wurden nicht gegen Produktionsdienste getestet.

4. Korrigierte Fehler während der Prüfung

Beim ersten mobilen Testlauf scheiterten zwei Tests der Legacy-Speicherquarantäne: Die Kopie verwendete bereits den isolierten Schlüsselpräfix tracebackend., die Testdaten noch sctracker.. Nach Anpassung der Testdaten wurden sämtliche mobilen Tests erneut ausgeführt und bestanden. Der endgültige Lauf ist im Paket enthalten.

5. Prüfungen wiederholen

# Backend (Node 24)
cd backend
npm run typecheck
npm test

# PostgreSQL-Prüfung auf Windows x64
npm run test:integration:windows

# Mobile
cd ../mobile
npm run typecheck
npm test
npm run export:ios

# Web-Hilfsfunktionen und Rollen
cd ..
npm test

Die Windows-Datenbankprüfung erzeugt lokale Testdaten unter backend/.test-runtime/. Sie ist kein Migrationsbefehl für Ihre Anwendungsdatenbank. Die aus der Laufzeitumgebung stammenden Testdaten und Passwörter sind nicht im Dokumentationspaket enthalten.

6. Noch erforderliche Abnahme

  1. Vollständige Datenbankmigration einschließlich PostGIS und RLS mit den vorgesehenen Rollen.
  2. S3-Integration mit gültigen/abgelaufenen Upload-Berechtigungen, Wiederholungen und Prozessabbruch.
  3. Zwei reale Geräte bearbeiten dieselben Daten offline und lösen Konflikte auf.
  4. iPhone: Flugmodus beim Token-Refresh, Hintergrundwechsel, App-Neustart, GPS-Verweigerung und Dateiübertragung.
  5. Browser: vollständige Bedienwege aller Rollen, besonders Freigabe und DDS-Klärung.
  6. Fachliche Prüfung des DDS-Datenmodells und Abnahme einer echten externen Übermittlung.
